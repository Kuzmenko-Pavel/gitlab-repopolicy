# Випуск релізу

Реліз - це підписаний тег `vX.Y.Z` на main, повторні перевірки на його коміті й артефакти, які споживач перевіряє двома командами ([install.md](install.md#1-завантажити-й-перевірити-реліз)). Документ для мейнтейнерів.

## Версії

- Тег - `vX.Y.Z` або `vX.Y.Z-rc.N`, інших форматів немає. `v` потрібен Go modules
- У бінарнику, іменах архівів, пакетах і audit версія без `v`: `1.0.0`. У метаданих deb і rpm pre-release записується з тильдою (`1.0.0~rc.1`), щоб пакетний менеджер упорядкував його перед `1.0.0`
- SemVer. `-rc.N` публікується як pre-release на GitHub
- `version: 1` у policy-файлах не пов'язана з версією бінарника
- Текст релізу - повідомлення тегу без блоку підпису. Окремого `CHANGELOG.md` немає

## Хто може підписати реліз

Ключі, якими дозволено підписувати релізні теги, лежать у [TAGPOLICY](../TAGPOLICY) самого проєкту. Перед публікацією workflow перевіряє підпис тегу цим файлом - тим самим кодом, що й hook на GitLab. Новий підписант додається pull request'ом з його публічним ключем OpenPGP: історія прав на реліз - історія цього файлу.

Створювати, переміщувати й видаляти теги `v*` на GitHub може лише власник репозиторію (правило репозиторію).

## Як випустити

1. Переконайтеся, що main зелений: `ci` і `e2e` на останньому коміті
2. На актуальному main без незакомічених змін:

   ```sh
   make release RELEASE_VERSION=1.1.0
   ```

   Target перевіряє гілку, чисте дерево і збіг з `origin/main`, збирає changelog з Conventional Commits від попереднього релізу (для `-rc` - від попереднього тегу, для фінальної версії - від попереднього не-rc), розкладає його на розділи (Breaking changes, Features, Fixes, Performance, Dependencies, Other changes) і створює підписаний annotated-тег, відкриваючи редактор для перегляду тексту. Без `RELEASE_VERSION` версію буде запитано.

3. Запуште тег:

   ```sh
   git push origin v1.1.0
   ```

Далі все робить workflow `release.yml`.

## Що робить `release.yml`

1. **Перевірка тегу** (`make code-build release-verify-tag`): тег annotated, формат версії допустимий, коміт тегу лежить у main, підпис тегу приймає `TAGPOLICY` проєкту. Інакше реліз зупиняється
2. **Ті самі перевірки, що й для pull request**, і повна e2e-матриця на коміті тегу. Integration додатково перевіряє відкат: попередня minor-версія, перевірена як споживач, приймає весь валідний корпус PATHPOLICY і TAGPOLICY
3. **Публікація** (`make release-publish`): GoReleaser збирає `linux/amd64` і `linux/arm64`, архіви, deb і rpm, SBOM, `checksums.txt` і keyless-підпис cosign, створює GitHub Release з текстом тегу. Потім target завантажує опубліковані артефакти і перевіряє їх так, як це зробить споживач
4. **Attestation**: SLSA provenance для файлів релізу

Якщо реліз не вдався, виправлення йде новим тегом. Опублікований тег не переміщується.

## Відтворюваність

Той самий тег дає побайтово ті самі бінарники. Nightly перевіряє це для останнього релізу:

```sh
make release-reproduce
```

Target збирає бінарники з коміту тегу і порівнює їхні sha256 з бінарниками з архівів релізу.

## Перевірка без публікації

```sh
make release-snapshot
```

Повне пакування без підпису і публікації, у `dist/`. CI виконує його на кожен pull request, щоб поломка конфігурації пакування з'являлася до тегу.
