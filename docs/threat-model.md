# Модель загроз

gitlab-repopolicy захищає вміст захищених шляхів, формат історії та релізні теги від усіх, хто може робити push, але не керує проєктом. Налаштування проєкту поза його досяжністю - це головний залишковий ризик, і його компенсує лише виявлення (`settings-check`).

Безпека інструмента не залежить від таємності коду: усі обмеження описано тут публічно.

## Межа довіри

Hook запускається лише для змін гілок і тегів і лише після штатної перевірки прав GitLab. Він може відмовити, але не може дати прав.

Поза межею довіри - ті, хто змінює GitLab або Gitaly в обхід приймання push:
- Owner проєкту й namespace: recovery за задумом, transfer, видалення, імпорт
- адміністратор GitLab: impersonation, керування членством
- root на ноді Gitaly і користувач `git`: запис у репозиторій в обхід hooks

Maintainer - частково: його зміни в git обмежені, а налаштування проєкту - ні.

## Обходи через налаштування проєкту

Hook викликається лише тоді, коли змінюється гілка чи тег. Зміни в Settings - це запис у базу GitLab, hook їх не бачить. Усі обходи потребують ролі Maintainer:

| Дія Maintainer | За `refs: all` | За `refs: protected` | Компенсація |
| --- | --- | --- | --- |
| "CI/CD configuration file" на незахищений шлях, інший проєкт або URL | **обхід** | **обхід** | `settings-check` |
| push зміненого CI у звичайну гілку, потім захистити гілку | закрито | **обхід** | `refs: all` за замовчуванням |
| зробити default гілку без policy-файлів або зі старими версіями | закрито, якщо задано `default_branch` | закрито, якщо задано `default_branch` | hook відхиляє кожен push у проєкт, де default branch не зі списку `default_branch`; ефекти без push (ручний запуск pipeline, `CI_DEFAULT_BRANCH`) виявляє `settings-check` |
| увімкнути push через `CI_JOB_TOKEN` | **обхід**: job пушить від імені того, хто запустив pipeline | **обхід** | `settings-check` |
| pipeline variables, щоб змінити поведінку job | поза моделлю | поза моделлю | мінімальна роль для pipeline variables |

Якщо в `default_branch` кілька імен, наприклад `[main, master]` на час міграції, перемикання default між ними - прийнятий ризик: обидві гілки інсталяція назвала допустимими сама.

`settings-check` - це виявлення за розкладом (за замовчуванням раз на добу), а не запобігання: зміну, яку повернули між двома запусками, він не побачить. Повністю цю групу обходів закриває лише організаційний захід - роль Maintainer тільки у власників захищених шляхів. Там, де це неможливо, `settings-check` обов'язковий.

## Від чого захищено

- **Зміна захищених шляхів** будь-яким шляхом: push по HTTPS і SSH, merge кнопкою, auto-merge, Web IDE, API, revert і cherry-pick в UI, push із CI. Hook бачить ідентичність того, хто вносить зміну, а не автора коміту
- **Послаблення правил у тому ж push.** Policy читається з default branch до push; новою версією policy не можна скористатися для самої себе
- **Гілка зі своєю слабшою policy.** Один якір на весь push
- **Підробка автора.** Author, committer і підписи комітів для авторизації не використовуються
- **Deploy key, створений admin'ом.** Не людина, відмова на захищеному шляху
- **Push options клієнта** на рішення не впливають
- **`refs/replace/*`.** Дочірні git ігнорують replace refs, тож підмінений об'єкт не сховає зміну
- **Відкат файлу force push'ем** у default і protected гілках - теж зміна, вона перевіряється
- **Evil merge.** Шлях, змінений у самому merge-коміті, видно як зміну
- **Підпис staging-тегу під ім'ям prod-тегу.** Ім'я в об'єкті тегу звіряється з ім'ям, під яким його пушать
- **Невизначеність.** Збій API, прострочений токен, service account без доступу, невалідна policy, внутрішня помилка - відмова на захищеній зміні. Збій API ніколи не вмикає recovery
- **DoS через вхід.** Ліміти розміру, кількості правил, часу і викликів API; regex у TAGPOLICY і посиланнях COMMITPOLICY - RE2 з лінійним часом, `pattern` - з таймаутом

## Поза моделлю

- Проєкти й fork в особистому namespace не перевіряються. Зміни з них потрапляють у групові проєкти через merge, який перевіряється
- Імпорт і експорт, відновлення з backup, transfer проєкту - операції Owner і адміністратора
- Між читанням якоря й оновленням гілки минають мілісекунди. Для default branch git сам відхилить застарілий стан
- Поведінка коду, який захищений CI збирає й деплоїть: gitlab-repopolicy захищає pipeline, а не застосунок
- Rename або видалення користувача звільняє username. Якщо його займе інша людина, вона отримає права з policy, доки policy не виправлять. `settings-check` повідомляє про principals, яких більше немає
- Нова гілка або тег на старому коміті, що вже лежить у захищеній гілці, PATHPOLICY і COMMITPOLICY не перевіряються. Підпис такого тегу TAGPOLICY перевіряє
- Merge у незахищену гілку не приносить нових комітів: PATHPOLICY його не перевіряє, COMMITPOLICY перевіряє лише merge-коміт, а не влиті коміти, які вже є в репозиторії
- Скомпрометований приватний ключ підпису: до merge зміни TAGPOLICY, яка видаляє ключ, ним можна підписати реліз. SSH-ключ ще й не має строку дії: строк і окремий ключ для підпису - відповідальність того, хто додає ключ у TAGPOLICY
- Токен service account читає код, метадані й значення CI/CD variables усіх груп. На одній ноді Linux package це не більше, ніж уже має користувач `git`, від якого працюють Rails і Gitaly. За окремих нод Gitaly - прийнятий ризик: захищайте файл токена і ноди
- Сам GitHub-репозиторій проєкту hook не захищає: тут цілісність релізів тримають правила репозиторію і підпис артефактів ([release.md](release.md))
