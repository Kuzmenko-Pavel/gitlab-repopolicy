# Модель загроз

gitlab-repopolicy захищає вміст захищених шляхів, формат історії та релізні теги в репозиторіях проєктів від тих, хто може вносити в них зміни (push, merge, Web IDE, API), але не керує проєктом. Не перевіряються wiki, design і snippet-репозиторії, проєкти в особистому namespace і весь інстанс за `mode: off`. Налаштування проєкту поза досяжністю hook - це головний залишковий ризик, і його компенсує лише виявлення (`settings-check`).

Безпека інструмента не залежить від таємності коду: усі обмеження описано тут публічно.

## Межа довіри

Hook запускається лише для змін гілок і тегів і лише після штатної перевірки прав GitLab. Він може відмовити, але не може дати прав.

Поза межею довіри - ті, хто змінює GitLab або Gitaly в обхід приймання push:
- Owner проєкту й namespace: recovery за задумом, transfer, видалення, імпорт
- адміністратор GitLab: impersonation, керування членством
- root на ноді Gitaly і користувач `git`: запис у репозиторій в обхід hooks

Maintainer - частково: його зміни в git обмежені, а налаштування проєкту - ні.

## Актори

| Актор | PATHPOLICY | COMMITPOLICY | TAGPOLICY | Коментар |
| --- | --- | --- | --- | --- |
| Developer | захищає | захищає | захищає | ні push, ні merge в обхід; релізний тег - лише з дозволеним підписом |
| Maintainer | частково | захищає | частково | зміни в git обмежені, налаштування проєкту, зокрема default branch, - ні (нижче) |
| власник делегованої policy | за делегуванням | володіє правилами | володіє правилами | змінює й видаляє COMMITPOLICY і TAGPOLICY, але не PATHPOLICY |
| admin PATHPOLICY | за задумом | через PATHPOLICY | через PATHPOLICY | усі зміни в audit |
| Owner проєкту чи групи | ні | ні | ні | recovery за задумом; transfer, видалення |
| скомпрометований обліковий запис без права | захищає | захищає | захищає | обмежений своєю роллю |
| скомпрометований обліковий запис з правом | ні | ні | захищає | має право за визначенням; для релізного тегу потрібен ще приватний ключ підпису. Допомагають 2FA, SSO і audit |
| CI (`CI_JOB_TOKEN`) | захищає | захищає | захищає | job пушить від імені того, хто запустив pipeline, і перевіряється як він |
| deploy key | захищає | захищає | захищає | deploy key - не людина, навіть якщо його створив admin; для TAGPOLICY вирішує підпис |
| project чи group access token, service account | захищає | захищає | захищає | право - лише явним username у policy |
| адміністратор GitLab | ні | ні | ні | impersonation, членство |
| root на ноді Gitaly, користувач `git` | ні | ні | ні | запис в обхід hooks |

BRANCHPOLICY у таблиці немає, бо вона не розрізняє акторів. Правила однакові для всіх, хто може створити гілку. Вона обмежує, які гілки можна створити: `deny` забороняє клас, а ім'я, що не потрапило в жоден клас, не перевіряється. Заборонити все неописане можна правилом з `match: all` і `deny: true`. Вона підтримує домовленості про імена, але не є межею авторизації користувачів. За збою API перевірки `user_prefix` і `protected` пропускаються з попередженням, а вже наявні гілки не перевіряються.

## Обходи через налаштування проєкту

Hook викликається лише тоді, коли змінюється гілка чи тег. Зміни в Settings - це запис у базу GitLab, hook їх не бачить. Усі обходи потребують ролі Maintainer:

| Дія Maintainer | Результат | Компенсація |
| --- | --- | --- |
| "CI/CD configuration file" на незахищений шлях, інший проєкт або URL | **обхід** | `settings-check` |
| зробити default гілку без policy-файлів або зі старими версіями | закрито, якщо задано `default_branch` | hook відхиляє кожен push у проєкт, де default branch не зі списку `default_branch`; ефекти без push (ручний запуск pipeline, `CI_DEFAULT_BRANCH`) виявляє `settings-check` |
| увімкнути push через `CI_JOB_TOKEN` | **обхід**: job пушить від імені того, хто запустив pipeline | `settings-check` |
| зняти захист з release-гілки | вміст гілки не змінюється, а правило зі списком `match` діє за ім'ям гілки, не за захистом у GitLab | `settings-check` для BRANCHPOLICY з `protected: true` |
| pipeline variables, щоб змінити поведінку job | поза моделлю | мінімальна роль для pipeline variables |

Якщо в `default_branch` кілька імен, наприклад `[main, master]` на час міграції, перемикання default між ними - прийнятий ризик: обидві гілки інсталяція назвала допустимими сама.

`settings-check` - це виявлення за розкладом (за замовчуванням раз на добу), а не запобігання: зміну, яку повернули між двома запусками, він не побачить. Повністю цю групу обходів закриває лише організаційний захід - роль Maintainer тільки у власників захищених шляхів. Там, де це неможливо, `settings-check` обов'язковий.

## Від чого захищено

- **Зміна захищених шляхів будь-яким шляхом.** bob змінює `.gitlab-ci.yml` кнопкою Edit у UI, через API, revert або cherry-pick в UI чи push із CI. Hook бачить того, хто вносить зміну, а не автора коміту, і відмовляє так само, як на `git push`
- **Проміжні коміти.** bob пушить у `main` коміт зі зміненим `.gitlab-ci.yml` і наступний коміт, що його відкочує. Підсумковий файл той самий, але pipeline першого коміту виконав би зміну, тому в default branch, захищених гілках і гілках зі списку `match` перевіряється кожен коміт, що входить у гілку
- **Переписана історія в спільній гілці (B+).** bob робить rebase гілки з комітом alice і пушить свій новий вміст `ci.yml` у переписаному коміті. Hook пропускає лише вміст, який уже був у цій гілці або в default branch, тому новий вміст не сховати серед переписаних комітів
- **Вміст з чужої гілки.** bob створює гілку зі своїм `ci.yml`, а потім переносить цей вміст у спільну гілку rebase'ом. Дозволені версії файлу беруться лише з самої гілки і default branch, а не з інших гілок і тегів, тож чужа гілка не робить вміст "відомим"
- **Тег поза гілкою.** bob ставить тег на локальний коміт зі зміненим `.gitlab-ci.yml` і пушить лише тег. Pipeline тегу виконав би неперевірений коміт, тому тег приймається, лише якщо його коміт лежить у гілці після push
- **Послаблення правил у тому ж push.** bob видаляє своє обмеження з PATHPOLICY і в тому ж push змінює захищений файл. Правила читаються з default branch до push, тож нова версія діє лише з наступного push
- **Гілка зі своєю слабшою policy.** bob пушить гілку, де PATHPOLICY дозволяє йому все. Правила для всіх гілок і тегів беруться з default branch до push
- **Підробка автора.** bob пише коміт з `--author "alice <alice@example.com>"`. Author, committer і підписи комітів для рішення не використовуються
- **Deploy key, створений admin'ом.** Push deploy key'ем на захищений шлях відхиляється: deploy key - не людина
- **Push options клієнта** (`git push -o ...`) на рішення не впливають
- **`refs/replace/*`.** bob пушить replace ref, щоб змінений коміт виглядав як невинний. Hook ігнорує replace refs і бачить справжній об'єкт
- **Відкат файлу force push'ем.** bob force push'ем повертає `main` до коміту зі старим `ci.yml`. Різниця вмісту гілки до і після push - теж зміна
- **Evil merge.** bob змінює `ci.yml` у самому merge-коміті під час розв'язання конфлікту. Шлях, змінений у merge-коміті, видно як зміну
- **Підпис staging-тегу під ім'ям prod-тегу.** bob бере підписаний staging-тег і пушить його як `v1.4.0-prod`. Ім'я в об'єкті тегу звіряється з ім'ям, під яким його пушать
- **Невизначеність.** API GitLab не відповів, коли треба знати, хто bob. Збій API, прострочений токен, service account без доступу, зламаний файл чи пресет, внутрішня помилка - відмова на захищеній зміні. Збій API ніколи не вмикає recovery
- **DoS через вхід.** bob пише повідомлення коміту, на якому регулярний вираз працює роками. Усі регулярні вирази - RE2 з лінійним часом, плюс ліміти розміру, кількості правил і комітів, часу і викликів API

## Поза моделлю

- Проєкти й fork в особистому namespace не перевіряються. Зміни з них потрапляють у групові проєкти через merge, який перевіряється
- Імпорт і експорт, відновлення з backup, transfer проєкту - операції Owner і адміністратора
- Два одночасні push. Кожен запуск читає власний якір, а блокування всього репозиторію на час перевірки немає. Git звіряє старе значення ref, який оновлюється, але це не гарантує актуальності основної гілки для паралельного push в іншу гілку. Не покладайтеся на серіалізацію зміни policy й усіх інших push
- Поведінка коду, який захищений CI збирає й деплоїть: gitlab-repopolicy захищає pipeline, а не застосунок
- Rename або видалення користувача звільняє username. Якщо його займе інша людина, вона отримає права з policy, доки policy не виправлять. `settings-check` повідомляє про principals, яких більше немає
- Теги PATHPOLICY і COMMITPOLICY не перевіряють, тому ядро окремо вимагає досяжності їхніх комітів із гілок. Це не доводить, що стара історія пройшла поточні правила: вона могла з'явитися до їх увімкнення. Нова гілка на наявному коміті перевіряється відповідно до її класу й `match`, а TAGPOLICY окремо перевіряє підпис тегу під правилом
- Merge у звичайну гілку під `match: all` приносить лише вміст, який уже є в репозиторії: PATHPOLICY перевіряє тільки новий вміст, COMMITPOLICY - лише merge-коміт. Зміна буде перевірена, коли гілку зіллють у `main`
- Скомпрометований приватний ключ підпису: до merge зміни TAGPOLICY, яка видаляє ключ, ним можна підписати реліз. SSH-ключ ще й не має строку дії: строк і окремий ключ для підпису - відповідальність того, хто додає ключ у TAGPOLICY
- Токен service account читає код, метадані й значення CI/CD variables усіх груп. Це властивість GitLab для ролі Maintainer і scope `read_api`, hook цим не користується. На одній ноді Linux package це не більше, ніж уже має користувач `git`, від якого працюють Rails і Gitaly. За окремих нод Gitaly - прийнятий ризик: захищайте файл токена і ноди
- Сам GitHub-репозиторій проєкту hook не захищає: тут цілісність релізів тримають правила репозиторію і підпис артефактів ([release.md](../../development/release.md))
